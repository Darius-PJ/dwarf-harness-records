- **The mechanism, from every local passing run on record** (S1, S2 and S3 logs: focused, plain, race, ×20, smoke, RB1; 30 `native quota` lines): the Job's per-job user-time limit kills the payload only after its user CPU reaches **2.09–6.69 s** against the configured 2.0 s. Windows enforces `JOB_OBJECT_LIMIT_JOB_TIME` coarsely, and the observed overshoot reaches 4.7 s even without the replica's load. Under the replica's load the payload accrues CPU at about 0.4 CPU-s per wall-second, so the quota kill (2 s plus an overshoot of up to about 4.7 s) can fall after the Wall. F's 4.48 s lies inside the passing distribution, which means the kill simply had not happened yet. The base replica's run (setup 13.1 s, 2.09 s user) is the same race lost earlier.
- **Classification:** test timing under a load heavier than the hosted step's, the same test and mechanism as the base replica, which predates ticket 144's changes. It is not S1–S3's change (the companion payload is a plain build, and the base replica failed the same way with the race-built self image). The product reported a correct `TimedOut` with a positive closure, so no product containment failure is shown. The product's CPU limit is coarse: the kill can come seconds after the configured CPU time. Microsoft documents the per-Job user-time limit as a periodic check that terminates all processes with ERROR_NOT_ENOUGH_QUOTA (`JOBOBJECT_BASIC_LIMIT_INFORMATION`, `PerJobUserTimeLimit`); the interval is not stated. **Not established:** whether the kill's latency is bounded in CPU time or in wall time; both fit the two replicas. **Hosted overshoot: unmeasured,** since the race step runs without `-v` (`tools/check/race.go:29`).
