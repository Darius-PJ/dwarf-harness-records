# Ticket 144 — Windows executor race-step reliability

## For the owner

Two hosted failures are the same sandboxed fixture startup failure: ThreadSanitizer exits 66 before payload work. The third is a test observer rejecting a changing native PID snapshot, not evidence of a failed product closure: the final receipt says the whole tree exited and resources are reusable. Preserve all isolation and closure assertions; do not buy reliability with retries or larger time budgets. Proposed production-file ownership: **none**, subject to the diagnostic checkpoints below. Ticket 16 must be told if those facts require production changes. Sources: ticket 144 acceptance criteria 1–5 (`.scratch/dwarf-harness/issues/144-make-the-windows-executors-race-step-tests-reliable-on-hosted-runners.md:34-38`); the three hosted Windows job records cited in §0; `internal/core/winexec/matrix_supervisor_windows_test.go:159-176,267-324`; `internal/core/winexec/executor_windows.go:580-625,729-761`.

## §0. Failure mechanisms, ranked causes and discriminating evidence

These are source-based diagnoses, not new reproductions. Public citations below use run/job and log line only, never a private archive path. Existing local observations are corroboration, not hosted evidence and not a reason to weaken an assertion. ### 0.1 Run 40773519796 / Check / windows-amd64 / da18709 — native user CPU

**Mechanism and fired assertion.** `TestNativeUserCPULimit` runs the copied test executable in a real restricted Job with a 2 s native user-CPU limit. It requires quota exit (NTSTATUS mapped to 1816, or 1816), aggregate user CPU at least the configured limit, `cpu-ready`, tree exit and reusable resources. Actual failure is `executor_windows_test.go:152`, not the declaration line 144: exit 66, no stdout, user CPU 0, one process, peak Job/process memory 152,027,136 bytes, ThreadSanitizer's failed 8,388,608-byte allocation at fixed address `0x028000000000`, native 487. The fixture never reached its CPU work. Product closure succeeded. Sources: `internal/core/winexec/executor_windows_test.go:144-154`; hosted run 40773519796, Windows job, log lines 514–515; ticket 45 ruling `.scratch/dwarf-harness/c10-evidence/ticket-45-design-ruling.md:109-117,130-151`.

**Ranked causes.** (1) Strong: race-runtime fixed-address/startup interaction in the AppContainer/Job fixture; exact stderr, empty output and user time distinguish it from a CPU enforcement bug. The precise address-space collision/reservation trigger is **unestablished**. (2) Plausible but weaker: Job commit restriction interacting with TSan reservation; peak commit is below the actual shared 2 GiB profile (the CPU test overrides only UserCPU), and error 487 is not direct proof of exhausted commit. The helper comment conflates the CPU and memory rows; the memory row, not the CPU row, overrides commit to 256 MiB. (3) Load/image/ASLR differences may alter occurrence probability, not the observed failure mechanism; record, do not blame them without a controlled contrast. (4) Timing/deadline and shared state between parallel tests are unsupported as direct causes: execution lasted 49.6 ms and the native exit is an explicit TSan abort. Sources: same receipt; `internal/core/winexec/security_windows_test.go:24-76`; `internal/core/winexec/executor_windows_test.go:144-154`; `internal/core/winexec/limits_windows_test.go:201-206`; prior ruled distinction between 487 and commit errors at `.scratch/dwarf-harness/c10-evidence/ticket-45-design-ruling.md:134-146`.

**Discrimination.** One labelled diagnostic stage compares the identical race fixture with/without the Job memory limit (throwaway probe only), then the same behavior supplied by an uninstrumented test fixture while the supervisor remains race-built. Keep raw stderr, build identity, actual Job limits, phase recorder and accounting, not just pass/fail. A failure independent of commit limits rules out merely raising a test memory constant; a pass alone does not establish a limit cause for an intermittent failure. A child failing outside containment is routed to the toolchain/runner, not fixed in product code. Do not call the finer TSan trigger solved unless the contrast establishes it. Prior §8 explicitly requires bounded, one-factor probes and treats `-race` as host-executor instrumentation (`.scratch/dwarf-harness/c10-evidence/ticket-45-design-ruling.md:130-159`); ticket 144 bounds routing and bans concealment (`.scratch/dwarf-harness/issues/144-make-the-windows-executors-race-step-tests-reliable-on-hosted-runners.md:35-41`).

### 0.2 Run 41133154184 / Check / windows-amd64 / c2d42e4 — separate peer inputs

**Mechanism and fired assertion.** Two distinct executor roots/SIDs stop at `suspended_verified`; the host discloses each peer's actual input/work paths, releases both, then requires each own nonce and native access-denied (5) for both reads and both writes, with target bytes unchanged. The hosted failure was `assertReusable` at line 98: the fixture exited 66 with exactly the same TSan allocation/487, no stdout, user time 0, one process and 152,027,136-byte peak. It did **not** reach the native-denial assertion. Sources: `internal/core/winexec/matrix_security_windows_test.go:21-116`; hosted run 41133154184, Windows job, log lines 514–515.

**Ranked causes.** (1) Same proved startup mechanism as 0.1; finer fixed-address cause unknown. (2) A separate source-visible ordering defect can invalidate this test even when startup succeeds: either run may remove its own paths while the other still probes. The earlier private observation of four error-3 probes is consistent with that ordering, but is not the hosted failure. (3) Resource pressure/load and per-process address-space layout remain possible TSan triggers; neither shared-root nor shared-SID contamination is evidenced (the test asserts distinct identities). (4) A real access bypass is not observed: no probe ran in this hosted receipt, and error 3 in the other observation is not proof of denial 5. Sources: same test and log; cleanup follows tree exit at `internal/core/winexec/executor_windows.go:666-673,742-761`.

**Discrimination.** Share 0.1's TSan contrast. Independently impose a deliberate skew: hold peer B before resume and let A finish its probes first. On the old fixture, await A's completed run before releasing B to demonstrate the deleted-target window. On the fixed fixture, A explicitly acknowledges probe completion and remains live until B has also probed; both target sets remain present. Do not block A's tree-exit/cleanup observer and spend its stop grace while waiting for B. Keep exact four native errors, both own nonces and unchanged bytes. Do not accept error 3 as denial or merely release both children together. Sources: `internal/core/winexec/matrix_security_windows_test.go:35-65,93-116`; `internal/core/winexec/matrix_payload_windows_test.go:90-115`; ticket 144 criterion 3 and verification boundary (`.scratch/dwarf-harness/issues/144-make-the-windows-executors-race-step-tests-reliable-on-hosted-runners.md:36,40-42`).

### 0.3 Run 42338417245 / Check / windows-amd64 / a38ecb7 — nested Jobs and process limit

**Mechanism and fired assertion.** A real supervisor goes into an outer Job limited to four processes. Its run Job is limited to two; a live root/child pair denies an extra spawn with 1816. The parent verifies outer membership and unchanged limits, closes its observer process handles, releases the payload and requires an error-free final frame/reusable receipt. Failure at line 517 is `done.Error != ""`: `incomplete native Job PID list: {Assigned:1 Count:0 …}`. Yet the returned receipt has exit 0, `RootExited`, `TreeExited`, `ResourcesReusable`, sealed output and total processes 2. The printed `Active:1` and unconfirmed fence are the **last observation frame**, not a final product accounting/fence read. Sources: `internal/core/winexec/matrix_supervisor_windows_test.go:159-176,267-324,467-526`; hosted run 42338417245, Windows job, log lines 520–521.

**Ranked causes and product verdict.** (1) Strong, source-backed: test-only observer makes process-ID enumeration authoritative during asynchronous retirement. `testJobPIDs` rejects any Assigned/Count mismatch. `testRunFrame` invokes it at every phase, including `root_exited`; a failure is retained in `observationErr`, stops all later frame refreshes, cancels the test context and is joined into the final test frame after a successful Run. Product closure instead closes root references then requires `jobAccounting.Active == 0`; it never calls `testJobPIDs`. Therefore this log does **not** demonstrate a product defect; recommendation is a test-observer fix, not any relaxation of Job-zero or the durable fence. (2) An asynchronous native rundown window is supported by the bounded probe in private §0.4; that probe does not reproduce the exact hosted Assigned/Count pair or identify its phase. Retaining an exited process handle is not a deterministic way to manufacture that pair. (3) An unpinned buffer or malformed ABI is lower-ranked: `queryJob` already pins buffers; capture actual size/alignment and errors if a stable, held tree shows a mismatch. (4) Deadline/load, cross-test shared state or broken process-limit enforcement are weak: no deadline error, 0.56 s total, correct denial output and successful positive closure. Sources: `internal/core/winexec/matrix_process_windows_test.go:195-214`; `internal/core/winexec/matrix_supervisor_windows_test.go:267-324`; `internal/core/winexec/executor_windows.go:580-625,742-761`; `internal/core/winexec/job_windows.go:24-30`; same hosted receipt.

**Discrimination.** Record phase, accounting and PID-list header separately. The PM's native probe answered the retained-handle question (§0.4); do not repeat it merely to confirm it. A deterministic regression must force the observer's inappropriate dependency on a native query during a non-proof phase, rather than promise a deterministic native mismatch. Keep strict census at the paused `count-ready`/live-tree boundaries and native accounting at the positively closed boundaries. Do not retry a mismatched census, substitute PIDs for Job-zero, or make every observer error disappear. Sources: ticket 45 ruling `.scratch/dwarf-harness/c10-evidence/ticket-45-design-ruling.md:27,67,114-117`; ticket 144 criteria 2–3 (`.scratch/dwarf-harness/issues/144-make-the-windows-executors-race-step-tests-reliable-on-hosted-runners.md:35-36`).

## §1. Numbered design choices

Each P-choice is a proposal for the fresh advisor, not a new owner decision. Its detailed implementation below is part of the same numbered choice.

### P1 — Diagnosis before implementation

**Options:** three independent failure/fix slices diagnosing as they go; or one labelled, non-shipping diagnostic stage D0 followed by focused fixes. **Recommend D0 first**, because two test names share one failure mechanism and the third must not be misrouted as a product closure defect. ### P2 — Comparable local load, not arbitrary stress

**Options:** affected-package repetition only; synthetic CPU/memory pressure; or the check's exact race command/environment. **Recommend the exact race-step replica for diagnosis**, once on the base and once on the final code, with at most one further full-load diagnostic if a result needs discrimination. ### P3 — Race-instrument the executor, not an incidental contained fixture

**Options:** increase memory/time limits; replace only CPU with a native loop and duplicate peer probes in another language; prebuild through tools/check/workflow; or build one plain companion of the same Go test package and stage it as the payload while the host and real supervisors remain race-built. **Recommend the plain companion**, with one package-owned lazy build and existing TestMain cleanup (§2.1). The two hosted direct roots invalidate the former descendant-only workaround as a general cure; behavior rows cannot be replaced with held cmd children. A package-local companion uses the same payload implementations and unchanged containment, not skips/fallbacks. It avoids out-of-scope tooling/workflow changes. This asks the advisor to supersede ticket 45 §8.1/notes 26's assistant-level prohibition on a build inside tests; it does not change the pinned toolchain or add a module. The tradeoff is one additional cached plain package compilation per top-level race-test process, reported as fixture setup cost, not product capacity. Sources: `internal/core/winexec/matrix_security_windows_test.go:35-116`; `internal/core/winexec/matrix_payload_windows_test.go:90-115`; `internal/core/winexec/executor_windows.go:656-660,742-761,822-827`; ticket 144 criteria 2–3 at `.scratch/dwarf-harness/issues/144-make-the-windows-executors-race-step-tests-reliable-on-hosted-runners.md:35-36`.

**Options:** loosen `testJobPIDs`'s completeness check; retry enumeration; suppress all observer errors; or take strict native census only at the test's stable live-proof boundaries and native accounting at the closed-proof boundaries. **Recommend phase-specific proof**, retaining `testJobPIDs` byte-for-byte and all mandatory errors (§2.3).
