## §2 — Review requests and exact subjects

### 2.1 Meaning and typed entrances (P2, P4–P6)

`ReviewRequest` asks for one semantic `approve`/`reject` judgment of a **submitted** task's exact stored submission. `FailureRequest` asks for one explicit failure decision on an assigned task in `waiting`, `active` or `submitted`. Both are immutable requests; neither is a check run, dispatch, message delivery, model call or promotion request. A failure request on a submitted task names that exact submission; otherwise it names the exact authorized immutable object being judged. Sources: ticket 12:10-12,29-33,51; `docs/DESIGN-CORE-AND-LAUNCHERS.md:920`; `internal/core/agents/tasks.go:152-175`.

Add these service and bound-agent methods, following `TransitionTask`'s owner/agent entrances:

```go
// Service mutation methods additionally take origin Binding after ctx.
RequestReview(ctx context.Context, request ReviewRequest) (ReviewReceipt, error)
RequestFailure(ctx context.Context, request FailureRequest) (ReviewReceipt, error)
ResolveReview(ctx context.Context, result ReviewResult) (ReviewReceipt, error)
ResolveFailure(ctx context.Context, result FailureResult) (ReviewReceipt, error)
ReviewStatus(ctx context.Context, lookup ReviewLookup) (ReviewView, error)
ReviewCommandStatus(ctx context.Context, lookup ReviewCommandLookup) (ReviewReceipt, error)
```

`Service.ReviewStatus` / `Service.ReviewCommandStatus` are owner queries and, like existing passive owner task/status queries, need no origin parameter; `Agent` derives its fixed origin. Mutation methods on `Service` take a registered `origin Binding`, never an asserted actor. The host, not model text, selects the authenticated entrance. There is no external callback HTTP endpoint or authenticated bearer token in this ticket. Sources: `internal/core/agents/scoped_commands.go:43-61,97-128`; `internal/core/agents/scoped_task_query.go:14-49`; `internal/core/agents/doc.go:7-13`; `docs/DESIGN-CORE-AND-LAUNCHERS.md:329-339`.

The request's full `ReviewBinding` (§4) names **task ID/version, assignment ID/generation and assignee origin; reviewer principal and exact origin; subject; acceptance hash; concrete semantic-check and review-configuration artifact references; the exact nonempty required-evidence set; authorization revision; deadline**. Failure requests additionally name the proposed cause and one failing-evidence member. All enter the canonical command fingerprint. Results repeat and match this binding, not a task's current description, a same-hash substitute source, view selection or new assignment. Sources: ticket 12:29-32; `docs/ROADMAP-CORE.md:449-450`; `docs/DESIGN-CORE-AND-LAUNCHERS.md:920`; `docs/DECISIONS.md:186-190,407-415`.

**Check/config meaning (P4):** `check` and `config` are **real existing artifact references** declaring the semantic review's checklist/criterion and configuration. Their SHA-256 members are its check/config hashes. They are opaque immutable review inputs, not a `WorkspaceChecks`, trusted runner inventory, C4 gate receipt or assertion that automated checks passed. AcceptanceSHA256 equals the task's immutable acceptance-spec digest. Do not fill absent inputs with zero hashes, task descriptions by default, invented receipts or a made-up “no checks passed” artifact. The caller must name actual authorized sources; otherwise refuse. No general artifact-publishing endpoint is added. Sources: `docs/ROADMAP-CORE.md:449-450`; `docs/DESIGN-CORE-AND-LAUNCHERS.md:901-908,920`; `docs/DECISIONS.md:697-703`; `internal/core/agents/scoped_authority.go:164-179`.

### 2.3 One current request slot, explicit replacement (P5, P9)

At most one current request slot (either kind) exists per nonterminal task. A request does **not** increment task version/state. The slot records a durable required decision for that exact version/assignment and remains a guard after `reject` or deadline expiry; it is not a dispatch queue. A new request supplies `ReplacesRequestID`: absent only if no still-applicable slot exists; otherwise exactly the slot's current ID. Replacement may supersede pending/rejected/expired requests, but only with current request authority, exact current task expectation and a new request ID. No automatic retry, expiry callback, lease, timer or model turn. Sources: ticket 12:12,29-33; `docs/DESIGN-CORE-AND-LAUNCHERS.md:920`; `docs/DECISIONS.md:59-64,705-711`; `.scratch/dwarf-harness/spec.md:625-627`.

Cancellation, reassignment or any task-version change makes an unanswered request stale. Reassignment never transfers subject access or reviewer permission to a new context. An old slot cannot become applicable again even if hashes match. Its history remains queryable only under current authorization. A fresh assignment/version may have a new explicit request; this ticket does not impose review on every task. Sources: `docs/DECISIONS.md:50-53,407-415`; `contract/ledger/doc.go:1885-1900`; ticket-11 ruling P7/P8, `.scratch/dwarf-harness/c3-evidence/ticket-11-design-ruling.md:19-20`.

## §3 — Results, authority and task transitions

### 3.1 Guard order and idempotence (P8–P10)

A fresh mutation follows the existing lifecycle/principal/refresh/dedup/preflight discipline:

1. Refuse owner-supplied acting GrantID before lookup; derive registered origin/principal; reject mismatched Agent. Validate bounded typed input and canonicalize its full fingerprint.
2. Refresh; check current caller authority/read visibility before existence-sensitive request/task/receipt disclosure. Look up the command through authoritative catalogue/history; cache miss is not absence. Recheck the tail under the lock.
3. A matched same-principal/same-digest command returns its immutable receipt **before** task/slot CAS, deadline and new-work producer/capacity limits. Current caller authorization/read access still applies, as for scoped retries. Changed digest/principal is mismatch or nondisclosing denial, never a new decision. A duplicate after the original deadline acknowledges history; after revocation it is denied without effect.
4. New callback: exact immutable request, named reviewer/kind, binding/digest, request version 1/unanswered, current slot; exact task version/assignment/generation/assignee/stored submission; same authority revision and current participant/subject permissions; trusted time not past deadline. Do these before capacity.
5. Apply finite producer bounds/preparation reservation; prepare metadata/source witnesses outside the lock. Before one Submit, refresh/repeat authority, task/slot/reviewer/clock guards. Validate the **whole** group with Open's reducer. No external work under the lock.
6. One Submit, projections/book before acknowledgement. Cancellation cannot abandon a committed fact; uncertain write poisons the service.

Sources: ticket 12:10-12,29-33; `internal/core/agents/doc.go:16-22,79-94,172-184`; `internal/core/agents/scoped_execute.go:119-231`; `internal/core/agents/scoped_commands.go:30-47`; `docs/DECISIONS.md:669-675,705-711`; `contract/ledger/doc.go:1953-1987`.
