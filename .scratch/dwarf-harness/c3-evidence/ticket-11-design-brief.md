## §2 — Authenticated authority and grants

### Authenticated entrance (P2)

`Service.BindAgent(ctx context.Context, b Binding) (*Agent, error)` is a **trusted-host-only binding operation**. It verifies the registered agent/context and derives the sole session; it does not grant an operation. The host authenticates which agent connection/turn owns the binding before minting this object. `Agent` has unexported service/binding/session fields, no exported constructor, no actor setter and no access to its owning `Service`. Its methods accept no replacement origin, agent, session or context. A nil/unbound entrance or closed owning Service refuses. The object fixes ingress identity, **not permission**; every use reads current ledger-derived grants. No handle, secret or service-incarnation identifier enters a submission or record. Reconnecting mints a new entrance for the same registered identities and cannot resurrect grants. In-process host trust is explicit; a hostile same-user process is not contained by a Go type. Sources: R10:14; AS/doc.go:7–23; AS/service.go:150–158; CORE:504–522; SPEC:413–417.

Owner commands retain `Service` as their trusted owner-only entrance; each new owner command has an explicit registered `Origin Binding`, derives `actor=owner`, and identifies its target separately. Owner inspection never invokes `Agent` as the inspected agent. An `Actor` supplied in model text or request JSON is not accepted. Internal completion/reconciliation commands derive `actor=core`, and are host-only, not methods on `Agent`. Sources: CORE:487–489,942; DEC:D90–D93,B31; SPEC:413–419; P2.

### Grant form and attenuation (P3–P5)

A grant is immutable except for a separately recorded revocation. Required fields are its ID, issuer principal/origin, fixed grantee agent/context, parent grant ID (absent only for an owner root), a sorted operation set, sorted concrete resource set, one closed data class, explicit recipient-context set, finite local-unit allowance, finite maximum turn concurrency, finite per-operation bytes, remaining delegation depth and lifetime `until_revoked`. Task-execution grants additionally bind exact task ID and assignment generation. §6 defines encoding. No grant inherits a role's rank, gives access to another context's private files, reserves resources in advance or authorizes paid work. Sources: CORE:928–930; DEC:D82,B7,B9; SPEC:413,419.

Only the owner issues a root. An agent issues a child only with a current parent containing `grant.issue`, an explicitly owner-authorized delegation entrance for that context, the intended recipient in the parent's recipient set, and positive remaining depth. This is the explicit Orchestrator authorization D82 requires; it does **not** invent a C6 role registry or infer authority from the word Orchestrator. The grant is an authorization to delegate the named region; possession does not make that region readable by the delegator. C6 may later require its actual role/membership state as an additional condition. Sources: DEC:D82,B7,B8; CORE:930,938; CON:39,42; P3.

Child operations/resources/recipients must be subsets; its data class must be identical; its bytes, local units and concurrency may not exceed the parent; remaining depth must be strictly smaller; any task/generation restriction must be retained. No union of two grants may manufacture one broader grant or operation: one selected leaf and its complete ancestor chain must authorize the **whole** normalized operation. Shared ancestors appear once in its BudgetBook scope set. The parent ceiling is shared across all children, not copied into each child as fresh allowance. An owner expansion is a new root grant; neither agent renewal nor reassignment retargets an old one. Sources: D82; CORE:926–930; SPEC:419; ROUTE:899–918; P3,P9.

Containment also applies to task-creation audiences and assignment destinations: every selected recipient must be within the selected grant's explicit recipient set as well as the task audience. External grants contain exactly one external-effect operation (plus optional delegation controls), never a combined shell/process/network/connector/model permission. A child can add an exact task/generation restriction to an unrestricted parent, but cannot remove or replace an inherited restriction. Sources: D82; CORE:930; SPEC:413; P3,P5.

Resource containment is semantic and closed: context binding/scope must match and child slots are a subset; task ID must match; workspace ID/binding must match and child prefix equals/is a component descendant of the parent prefix; artifact source/hash/bytes and external resource key must match exactly. Different resource kinds cannot contain one another. The same containment rule compares a concrete operation target with its selected grant. Sources: SPEC:413; CORE:930; D82; P3,P5.

Version 1 chooses **no wall-clock expiration** (P4). Lifetime is explicitly until revocation, additionally ending for execution when the bound assignment generation ceases to be current. A child cannot outlive a revoked ancestor. No timer, inferred lease, UUID-time authorization or expiry placeholder is introduced. A later timed-lifetime producer needs an additive specified/frozen change; the owner can revoke now. This is a proposed resolution of “expiry if any”, not a claim that the sources selected a timeout. Sources: assignment:80; CORE:930; DEC:D37,D82.

An assignment-scoped grant loses all uses when its generation is no longer current. A separately explicit context-only grant may still permit read-only access to that agent's **own retained** old context; it conveys no current task/shared-artifact or effect permission. For task-bound-context mutations/turns/local effects, current assignment remains mandatory regardless of a broad context grant. Thus reassignment fences new task effects without pretending to erase the old private history, while every retained read still checks its actual present grant. Sources: D21,D82; CORE:474–485,920,930; SPEC:87,413; P4,P8.

`IssueGrant` and `RevokeGrant` CAS on `ExpectedAuthorityVersion`; each successful authority group advances the colony authority version once, starting at 1. A revoke names one exact grant, is allowed to the owner or its still-authorized issuer with `grant.revoke`, and is irreversible. Descendants become unusable by ancestor checks; do not write one synthetic revoke per descendant. An identical command replays; a new command attempting to revoke an already revoked grant is a no-effect `already_revoked` refusal, not another revision. Root/issuer ancestry facts remain in history; retain only live chain state and bounded lookup indexes in memory, with cold history scans for retired IDs. Sources: T11:28–30; DEC:B3,B7,D82; AS/commands.go:121–160; P4,P12.

### “Current” and races

At entry, under the shared state lock after refreshing through `store.Durable()`, authenticate origin and check the concrete operation, target, data class, current task generation and every non-revoked ancestor. Repeat after any unlocked preparation, before the commit/effect handoff, and immediately before returning private bytes, metadata, counts, cursors or receipts. Authorization is one deterministic local check, not a model approval call. The lock gives a linearization point: a disclosure/effect authorized before a concurrent revocation may complete; one ordered after it may not. Rechecking does not claw back a previously disclosed buffer or undo a committed effect. A remembered `Allowed` result, admission, discovery result or receipt is never a future dispatch/disclosure permit. Sources: T11:28–30; D79,D82; CORE:504–522; SPEC:413–417; P2,P4.

## §3 — Tasks and authorized projections
### Task definition and ownership (P6–P8)

`CreateTask` supplies a new UUIDv7 task ID, `ExpectedVersion=0`, exact description bytes, acceptance-spec SHA-256, sorted dependency task IDs, explicit context audience and, optionally, an initial assignment to an existing unbound work context. Description is explicitly published for that task audience, not an alias to the creator's private object. Definition, creator, acceptance digest, dependencies and audience are immutable in version 1; changing the goal means a new task. Creation does not create a context, grant, paid allowance, review request, scratch or turn. Sources: CORE:920; SPEC:393–395,413–419; D82; P6.

Task version starts at 1 and advances by exactly one for each applied transition. Assignment generation starts at 0 unassigned, becomes 1 on first claim/assignment, and increments on reassignment. An assignment has a new immutable UUIDv7 assignment ID, assigner principal/origin and exact agent/context binding; no session is caller-supplied. A work context can be bound to at most one task for its lifetime. Claim/assign/reassign use an already-created, never-task-bound `work` context; a reassignment never imports the old context's private bytes, scratch or grant. Preserve historical bindings in the ledger; do not interpret the latest task pointer as ownership of earlier context artifacts. Sources: CORE:454–457,920; RC:444–450,478–485; AS/service.go:150–158; D21,D22,D82; P8.

Every mutation supplies task ID and `ExpectedVersion`; every mutation after assignment also supplies `ExpectedAssignmentID` and `ExpectedGeneration`, except a first claim/assign which requires both absent/0. Compare them against current state under `Service.mu` immediately before Submit. A race loser gets `RevisionError`/`AssignmentError`, no record and no consumed command ID. Reassignment requires the exact old assignment, not merely the intended new recipient; a delayed start/submit/complete cannot affect its replacement. A current task-scoped grant checks its generation as well as task version expectations. Sources: T11:30,33; CORE:920; SPEC:83,413; P7,P8.

| Transition | Allowed source → destination; additional predicates |
|---|---|
| `create` | absent → `waiting`; optional assignment generation 1, otherwise 0. Dependencies already exist, are distinct, not self; because only creation adds dependency edges, new-ID-to-existing-ID edges cannot form a cycle. |
| `claim` | unassigned `waiting` → assigned `waiting`; the caller's agent is the assignee; its explicitly authorized claim operation names that task and intended fresh context. No “first wins” outside CAS. |
| `assign` | unassigned `waiting` → assigned `waiting`; owner or currently authorized assigning entrance chooses a recipient already in the immutable audience. |
| `start` | assigned `waiting` → `active`; all dependencies are `completed`, no wait reason, current assignment and execution grant match. This is a task-state declaration, **not** a StartTurn, model dispatch or completion claim. |
| `wait` | `active` → `waiting`; required closed reason `dependency`, `input`, `review`, or `explicit_hold`, and optional bounded authorized artifact reference. Does not cancel a turn, child or reservation. |
| `resume` | assigned `waiting` with a wait reason → `waiting` with it cleared; never bypasses a still-unsatisfied dependency or missing grant. No automatic turn. |
| `submit` | `active` → `submitted`; requires one exact immutable artifact reference supplied by the caller, stored as the current submission identity. No review callback is created or accepted. |
| `complete` | `submitted` → `completed`; requires current `task.complete` authorization, exact stored submission reference and assignment expectation. Owner/direct-authority completion is an explicit task decision, not validated promotion or a reviewer result. An agent's `task.submit` alone is insufficient. |
| `fail` | assigned `waiting`, `active`, or `submitted` → `failed`; requires a bounded cause code and exact immutable evidence artifact reference. This is a direct authorized transition, not ticket 12's FailureResult callback. |
| `cancel` | any nonterminal state → `cancelled`; authorized cancellation affects the task only, not an already-intended external operation or promotion. |
| `reassign` | assigned nonterminal state → `waiting`; new assignment ID, generation+1 and fresh work context; clears wait/submission/cause, preserves definition. Old task-grants no longer authorize new work/disclosure because their generation fails. It does not claim to cancel a running old effect or discard its context history. |

`completed`, `failed`, `cancelled` are terminal; no retry/reopen transition. New work uses a new task. Agent start/wait/resume/submit/fail must originate in the current assigned context; assigning/reassigning/completing/cancelling additionally require their own explicit operation grant, never supervisory rank. Owners retain their distinct entrance. Before ticket 12, direct complete/fail do not assert review, check acceptance or delivery; no generic “result” callback accepts agent reports. Later exact-subject records may add references without changing these version/generation facts. Sources: CORE:920; SPEC:81–89,393–395,413; T12:10–12; D52,D79,D82; P7.

Future exact-subject review/evidence guards must be enforced by this same complete transition, not bypassed by a generic direct complete operation. F3-11 creates neither a review requirement nor evidence that such a requirement passed; ticket 12 owns those actual guards/results. Sources: T12:12; CORE:920; SPEC:413; P7.

### Ready, blocked, active views

`TaskStatus` and bounded `ListTasks` return authorized immutable task facts plus current derived readiness, at a ledger high-water. `waiting` includes self-claimed and delegated assignments: **ready** only when assigned, dependencies completed, no explicit wait reason, current execution authorization and local admission configuration permit the work; **blocked** otherwise, with distinct currently-authorized reasons. `active` and `submitted` are separate facts, never waiting stockpile counts. Lack of a free turn slot is `ready_queued`, not permission denial or an invented age-based stall. An unassigned task is `waiting_blocked/unassigned`; no view diagnoses staffing. A revoked/invisible dependency yields an opaque `dependency_unavailable` reason, not its hidden title, state or existence. Terminal tasks are queryable by exact ID with current access but leave the live waiting/active projection. Sources: RC:428,494–495,507–508; D90–D92; CORE:922; SPEC:413; P6,P7.

Task state is independent of animal animation, inbox volume, session focus and whether a model is running. Queries recompute authorization/readiness from the current projection and return no hidden-task count, skipped-ID cursor, unauthorized body hash or stale cached row. List ordering/cursors use authorized task IDs in UUID-byte order with a bounded `AfterTaskID`; changing authority can remove rows between calls, never grant a snapshot right to later pages. Sources: D90–D92; CORE:922,942; SPEC:413; P6.


## §4 — Non-paid admission and the single BudgetBook
### One BudgetBook (P9)

Add a concrete unexported `budgetBook` inside `agents.Service`; it owns **all** local admission decisions in this ticket and is rebuilt by the same reducer. Its durable facts are owner-set finite limits, consumed local units, and unended durable work reservations. It has no JSON/config wallet, separate appender or backend-specific copy. Short-lived preparation/buffer reservations also live here, under the same lock, but are not durable work: before private/task publication commits there is no external effect to recover. They vanish at process death and cannot acknowledge success. Do not add pending private writes, repeating ticket 10's rejected design. Sources: T11:31–33; CORE:924–930; SPEC:393–395,419; R10:P7; P9.

`ConfigureCapacity` is an owner-only CAS command over one exact scope (`colony`, `agent`, or `context`) and its configuration version. Required finite non-negative fields are `turn_slots`, `local_slots`, `buffer_bytes`, `local_units`, and `max_operation_bytes` (§6's Capacity object); zero slots/units disable new work of that kind. Agent turn_slots is 1–3 when enabled (0 disables); context is 0 or 1. Colony values are explicit, never derived from available money. A root grant adds its own finite allowance/concurrency/bytes; every child adds an attenuated scope. A task attempt additionally binds its current assignment, not a fresh allowance. Missing required colony/agent/context enrollment means busy/capacity_unconfigured, not denial/unlimited. Lowering limits below used/held exposure never cancels, clips or resets it. Owner configuration, passive queries, revocation and honest release controls remain usable without ordinary local allowance. Sources: SPEC:413–419; CORE:924–930; RC:437,492–495; D22,D82; P9.

Applicable scopes are a sorted, de-duplicated set: colony, bound agent, bound context, selected grant leaf and every ancestor. For each scope, capacity admission checks **all** reusable resources atomically:

- turn work holds one `turn_slots` until its recorded terminal ending;
- durable local-tool admission holds one `local_slots` and its declared maximum `buffer_bytes` until terminal ending;
- private/artifact read or private-write preparation takes the same local/buffer resources transiently, before retaining copied bytes;
- one local_units hold/charge belongs to each durable local-tool admission, successful atomic Agent private/artifact read/write, Agent task mutation or Agent delegated issue. Admission holds it; dispatch/success converts it once to consumed. Unsent abandonment releases it; dispatched failure still consumed it. Turn admission itself, owner administration, passive metadata, revocation and endings consume no local unit. Charges remain for the scope's lifetime, without a clock period/reset.

`occupied = durable holds + live preparation holds`; for local units add durable consumed units. Use checked signed-64 integer arithmetic, never floats, wraparound or negative release. Grants authorize work but add no reservation at issuance. An attempt appears once per scope, even if the same grant ancestor is reached twice. Atomic private/task operations record their local charge with their effect; same-ID retries do not charge again. Configuration changes never reset lifetime usage; a deliberate new root grant does not reset colony/agent/context consumption. Sources: D22,D82,B9; CORE:924–930; ROUTE:899–921; P9.

The existing finite Limits.MaxConcurrentWrites and object/operation bounds still govern shared owner/Agent preparation; reuse their reservations, not an extra byte copy before admission. Transient preparation reservations are not extra durable units: the atomic final commit converts/relinquishes the same reservation. Sources: AS/types.go:23–35; AS/commands.go:175–202; R10:P7; P9.

This ticket does **not** implement paid money, tokens, credential/account scopes, tariffs, accounting periods, unknown paid holds or a provider reservation record. ### Bound StartTurn (P10)

`StartTurn` is an actual immediate admitted-or-busy typed command. It binds command ID, newly supplied turn UUIDv7, the entrance's fixed agent/session/context, selected grant ID, optional exact task/assignment/generation, `ExpectedTurnVersion=0` (no live turn), and current authority. It checks private integrity, current assignment/grant and all capacity scopes under the lock, then records one admission+receipt group, installs its durable slot reservation and context/agent active indexes, then acknowledges. No provider/model-call grant, paid consent or API key is needed because it starts no paid work. It renders no prompt and executes nothing; the receipt outcome is `admitted`, not `running` or `completed`. Sources: T11:31–33; RC:437,492–495; CORE:918,924–930; D22; P10.

If the context is task-bound, StartTurn must name its exact current assignment and the task must be active, not waiting/submitted/terminal; general work omits task_binding. Task readiness may justify an explicit task.start first, but assignment or inspection cannot start a turn implicitly. BeginLocal rechecks that same active task predicate. No C8 role/Purpose/activation fact is fabricated; later generic eligibility guards must join this same admission predicate when their producer exists. Sources: CORE:918–922; SPEC:403–413; T15:12; P7,P10.

A second distinct turn for the context is `busy/context_active`; a fourth across one agent is `busy/agent_capacity` even when colony capacity remains. A configured agent limit of 1 refuses its second. Fresh authority checks precede these capacity checks, so an unauthorized request gets `denied`, never a capacity disclosure. Identical command/digest replays its original admission, even if slots are now full or the turn has ended, subject to current authorization for the receipt; a different digest under that command ID is mismatch. No implicit queue, retry, goroutine per context, scheduling rotation or second session is added. Ticket 15 consumes the existing admitted facts through its fair scheduler. Sources: RC:437,445,492–495; CORE:918; AS/commands.go:121–181; P10,P12.

Host-only `EndTurn` CASes admitted version 1 to ended version 2, with exact turn/binding/admission identity. Version 1 writes outcomes released/cancelled/interrupted; released means admission release, not model success. Any unfamiliar preserved ending token is nonterminal/held, never success. Refuse while a child admission/other derived hold remains unended. Agent CancelTurn requires current turn.cancel on its own child-free admission; owner cancellation is distinct. Core honest interruption/release does not require a revoked agent grant. Endings never settle paid/tool/child holds by inference. Same-ID end replays; a different command against terminal work is already_terminal. Sources: SPEC:403–409; D37,D79,D82; CORE:918; P10,P15.

### Local-tool admission versus execution (P11)

`AdmitLocal` binds a new work ID, the currently admitted turn/binding, exact operation/target from §2, immutable normalized argument SHA-256, tool-schema version 1, explicit `MaxBytes`, selected grant and current assignment. It reserves all scopes in one durable group, returns `admitted`, and performs no file/process/network effect. `BeginLocal` is a **host-only dispatch transition**, not an agent-exposed permission token: exact work/version, argument digest and original target must still match; refresh and recheck current authority, assignment, parent turn and shutdown/cancellation state, then record `dispatched` and the one local-unit charge before handing that immutable request to the owning executor. This is not a command that executes arbitrary caller code or accepts a callback. Ticket 11 has no file executor; its observable deliverable is the durable admission/dispatch boundary, not a fabricated successful tool result. Sources: T11:10–12,28–33; T15:10–12; SPEC:393–395,413–419; D79,B7; P11.

Only `file.read/search/write/edit` admits a future local-tool handoff here. External classes may be evaluated against their separate grants, but execution admission returns `unavailable/producer_absent`, consumes nothing and runs nothing. A local admission is not allowed to change operation or acquire shell/network/model effects in its arguments. `BeginLocal` must be placed at the actual immediate handoff by ticket 15; it is never a permit that can be queued and used after another revocation check would fail. Once a dispatch is ordered before revocation, its already-started effect may finish; revocation bars subsequent handoffs and disclosures. This ticket's tests prove the typed state and current checks only, not the later executor. Sources: T11:28–33; SPEC:413–419; D79,D82; P5,P11.

Host-only `EndLocal` binds work/version, original turn/operation/argument identity and observed outcome `released_unsent`, `succeeded`, `failed`, `interrupted` or `unknown`. `released_unsent` requires admitted, undispatched work and releases its held unit; dispatched work has already consumed one unit. Ending releases its local/buffer slots only when the trusted host proves the local invocation no longer owns them; `unknown` retains them and fences the parent turn. This version records no result text or generic callback acceptance. The executor that actually exists in ticket 15 owns evidence/results and any additional record freeze; no model-reported success accepted here. Private/artifact operations below are already complete in ticket 11 and use the atomic path rather than this durable external-work path. Sources: T11:33; SPEC:393–409; D37,B7; P11.

All outcomes are typed and distinct: `DeniedError` (authentication/authority), `BusyError{Reason}` (finite allowance/occupancy), `RevisionError`/`AssignmentError`, `ErrCommandMismatch`, `ErrUnavailable`, integrity, closed/poisoned and actual I/O errors. Do not disguise a denial as busy, suggest buying capacity for a revoked grant, or write a durable command for a pre-admission refusal. Authorized reason detail is bounded; inaccessible targets get no existence, amount or ownership detail. Sources: T11:28–33; SPEC:87–89,413–419; AS/types.go:11–20; P9–P12.

### One transition, one Submit

For each new mutation:

1. Enter Service lifetime tracking; authenticate/bind origin; validate bounded typed input and normalize sorted sets/targets; hash/copy exact byte inputs only within finite preparation reservations.
2. Refresh complete commits through Durable. Check current authority **before disclosing** whether an ID exists. Find a prior command through authoritative history before expected-version, integrity, allowance and capacity checks; the existing outside-lock prefix scan/under-lock tail refresh pattern closes duplicate races. Compare principal/origin/operation/digest, not digest alone. A different family under the ID cannot be taken as a receipt.
3. For a genuinely new operation, check current authority and task/assignment expectations, reserve finite preparation/resources, and publish/verify any body/private bytes outside the short state transition. Re-enter and repeat lookup/current checks after this work.
4. Under `Service.mu`, check actual expected entity versions, current complete grant chain, assignment, integrity and BudgetBook exposure again; preflight the same group decoder/reducer used on replay. Submit **one** bounded group with F0 command first and F3-11 receipt last. No model, Git, check, remote authorization or executor runs under the lock.
5. Treat Submit's actual committed range as authoritative; refresh all intervening groups, read the actual result/receipt and install complete projections before ack. On a private revision, complete its Core-managed materializations too. Cancellation after durable commit cannot abandon completion. On uncertain/poisoned store writes poison Service and require a new incarnation after store recovery.

These are the existing pattern, not a new entity framework or independent persistence hooks. Sources: T11:33; AS/commands.go:121–347; AS/replay.go:258–322; LS/commands.go:131–213; R10:P7–P9; SPEC:393–395; P12.

Current authority is required to replay/disclose a receipt, but **not** to erase its historical fact. If a grant was revoked, a correctly authenticated original agent may receive `denied` rather than the receipt; the owner can still inspect it. If still authorized, replay is before CAS/capacity and returns the original receipt even after a later reassignment or closed turn **only if its target's present disclosure policy permits it**. There is no extra execution or charge on replay. A retry of a completed authorized read re-verifies its pinned data and current permission; its old receipt does not guarantee that collected/corrupt content remains available. ## §7 — Recovery and integrity
`Open` extends the existing streaming replay; it consumes F0 command/pin/unpin as needed, F3-10, all ten F3-11 types and the existing F2 scratch types, with `AllTypes=true`. Unsupported consumed versions fail closed; unknown unconsumed records are skipped while their envelope sequences are still traversed. Apply one complete group into provisional copies, then publish all its effects together. Recompute grants, authority version, task/assignment histories, currently bound task contexts, BudgetBook used/held exposure and admission states exclusively from committed records; mutable files/cache/UI state cannot create an identity, grant, charge, task or turn. Historical authorization is checked at its ledger position, not against a later revocation. Sources: LD:130–154; AS/replay.go:236–322; CORE:849–859,918–930; D35,B3,B7; P13,P15.

Replay reads no clock, starts no timer/goroutine/child/model/tool, sends no pending work, writes no record and resumes no admitted turn. It preserves occupied durable slots and marks pre-open admissions `recovery_pending` in its availability projection; that is not another durable authority fact. `ReconcileAdmissions(ctx, EndingRequest)` is an explicit trusted-host call for **one** work ID/expected version/command ID at a time: admitted local work without dispatch is proven unsent and ends released_unsent; an unended turn can end interrupted only after all its child holds end; dispatched local work lacking a proven ending records unknown/retains resources. Repeating a recorded unknown returns that state, not another charge/record. No effect is rerun to discover what happened. Later EndLocal can record a trusted proven ending; no owner “assume success” bypass is added. Sources: D37; SPEC:395,403–409; T11:34; P10,P11,P15.

Missing/corrupt selected private objects, foreign Markdown and agent-wide versus context-local fences follow ticket 10. Complete/report stale Markdown from verified selected objects only, without a new revision; body collection affects artifact availability, never task/grant/receipt history. Malformed group, missing predecessor, wrong actor/binding, impossible attenuation, stale CAS, repeated identity/command, scope/charge mismatch, underflow/overflow, or a capacity violation shown by the records fails Open, not “empty cache”. Lower configured runtime preparation limits must not invalidate legitimate larger historical payloads. Sources: AS/doc.go:65–97; AS/integrity.go:112–166; LD:1675–1687; B3,B21; P13–P15.

Retain current tasks/grants/work and ancestors/dependency facts needed by them; terminal histories and receipts use bounded hot indexes plus authoritative cold scans. A missing cold entry is not proof of absent/revoked/completed state. Task context IDs cannot be reused after evicting a terminal task: check authoritative history on a candidate binding/ID. Do not add `state.json`, a task directory, a “budget.json” or snapshot until B3's measured trigger; no constant-space, startup-time or retention claim. Close fences ingress and drains actual in-flight private/body operations, but must not silently end durable admissions or settle their holds. Sources: B3,B21; AS/doc.go:16–29,59–65; R10:P8,P9; P1,P15.
